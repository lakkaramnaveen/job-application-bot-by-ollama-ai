# Security

## Reporting a vulnerability

Open a GitHub issue describing the class of problem without a working exploit, or contact the maintainer privately if the repo has private vulnerability reporting enabled.

## Threat model, honestly stated

This is an agentic workflow: an LLM reads untrusted web content (job postings) alongside your personal data (resume, FAQ answers, application history) and can act on both. That combination is the main risk surface. What this project does about it:

- **Untrusted-input rule**: `job_bot/matching/scorer.py`, `job_bot/generation/*.py`, and `job_bot/browser/linkedin_adapter.py` all treat scraped job-posting text and application-question text as *data*, never as instructions - every system prompt says so explicitly, and postings/questions are always placed in the user turn, never concatenated into the system prompt. The browser adapter also never follows a link found inside posting text; `load_description()` reads only the description element of the page the user's own search already navigated to.
- **Categorical eligibility gate is enforced in code, not just prompted**: `job_bot/matching/scorer.py` forces `should_apply = False` whenever the model's own `eligibility` verdict is `"fail"` (e.g. a posting explicitly requires citizenship or an existing clearance the resume gives no sign of), regardless of what the model set `should_apply` to. A prompt injection or a model mistake in the surrounding fields can't undo this specific check.
- **No stored platform credentials**: `job_bot/browser/session.py` uses a Playwright persistent profile - you log into LinkedIn once, manually, in a real browser window. The bot never sees or stores the password.
- **Personal data stays local**: resume, tracker database, browser session, blacklist, audit log, and Gmail credentials/token all live under `app/data/`, which is gitignored (see `.gitignore` at the repo root, and `tests/test_gitignore_guard.py` which fails CI if that protection is ever weakened). The only network calls this project makes are to the configured LLM provider (Claude API or your own local Ollama server), to LinkedIn via the browser, and - only if you've set up Gmail sync - to the Gmail API.
- **Secret redaction in logs**: `job_bot/safety/audit_log.py` regex-redacts Anthropic API key and Bearer-token shapes from every logged value before it's written, in case a caller accidentally passes one through.
- **Hard-coded safety ceiling**: `job_bot/config.py`'s `HARD_DAILY_APPLICATION_CEILING` (50) is enforced in `RateLimiter` independent of whatever `DAILY_APPLICATION_CAP` a user configures - a misconfigured or runaway `.env` can't remove the daily cap entirely.
- **Gmail sync is read-only and forward-only**: `job_bot/integrations/gmail_client.py` requests only the `gmail.readonly` OAuth scope - this project cannot send, delete, label, or otherwise modify your mail, by construction, not just by convention. `job_bot/integrations/gmail_sync.py` treats email content as untrusted data the same way job postings are treated (see the untrusted-input rule above), only ever updates a tracked job's status on an unambiguous single company-name match above a confidence threshold, and never moves a status backward or touches one already in a terminal state (`offer`/`rejected`/`withdrawn`/`no_response`) - so a garbled or misclassified email can leave a false positive log entry at worst, never silently overwrite a status you already confirmed by hand.
- **Dashboard has no authentication and is not meant to have any**: `job_bot/dashboard/server.py` binds to `127.0.0.1` only, never `0.0.0.0` - it is not reachable from your network, let alone the internet. It renders tracker data (job titles, company names, URLs) into HTML with `html.escape()` on every field (`job_bot/dashboard/render.py`), since that data ultimately comes from scraped LinkedIn listings and Gmail - an unescaped field would be a stored-XSS vector against your own browser. A job's `url` additionally goes through a scheme allowlist (`_title_cell()` in `render.py`, only `http`/`https` render as a clickable link) - `html.escape()` alone neutralizes attribute-breakout but not a `javascript:` URI, which contains no HTML-special characters and would otherwise execute in the dashboard's origin on click. This was found and fixed via a security review before this feature shipped; `tests/test_dashboard_render.py` has the regression tests.
- **Job IDs are validated before touching the filesystem**: `posting.job_id` comes from a scraped LinkedIn `data-job-id` DOM attribute - untrusted data - and is used as a directory name under `data/applications/` by `job_bot/generation/artifacts.py`. `_job_dir()` there rejects anything that isn't a plain alphanumeric/`.`/`_`/`-` string, and separately rejects the literal `.`/`..` components, before ever calling `mkdir`/`write_text` - so a malformed or malicious job ID can raise `UnsafeJobId` and abort the run, but can never write a file outside `data/applications/`. `tests/test_artifacts.py` has the regression tests (`../../etc/passwd`, bare `..`, embedded slashes, etc.).

Instruction-level defenses raise the bar; they are not a sandbox. If you point this at a job board or company career page you don't trust at all, use `--dry-run` first and review what got filled in before you let it actually submit.

## Scope notes

- LinkedIn's Terms of Service restrict automated use of the site. Running this tool is a decision you're making about your own account, not a claim this project makes on your behalf that it's compliant - see the "Before you use this" section of `README.md`.
- This project makes no attempt to evade LinkedIn's bot detection. It doesn't fingerprint-spoof, rotate proxies, or otherwise disguise its traffic as something other than an automated browser session - see `job_bot/browser/linkedin_adapter.py`'s module docstring.
- Gmail's OAuth consent screen will show your own Google Cloud project's name and the `gmail.readonly` scope being requested - review it before granting access, same as you would for any third-party app.
